# MADS v0.8.0 Machine-Readable CLI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add optional schema-version-1 JSON output to every finite existing CLI command while preserving default human text, Cargo/application streams, and the established 0/1/2 exit classes.

**Architecture:** Parse output selection into an invocation envelope before dispatch. Make each finite command return structured command data plus ordered diagnostics, then choose one human or JSON renderer at the outermost boundary. Convert the private inspection protocol into a separate public CLI record model; do not expose its wire schema. Keep `run` and `dev` on their direct streaming path and reject output selection before launch.

**Tech Stack:** Rust 2024, Rust 1.85 MSRV, Serde/Serde JSON, existing Cargo metadata and inspection transport, structured database reports, deterministic sorting/path normalization, `assert_cmd`, and Linux/macOS/Windows CLI tests.

**Spec:** `docs/superpowers/specs/2026-09-06-v0.8.0-diagnostics-machine-output-design.md`

## Global Constraints

- This is Plan 6 of 8 and begins after Plans 1-5 establish beta APIs and diagnostics.
- Default `human` output must remain byte-for-byte compatible except where the approved common diagnostic renderer intentionally replaces ad hoc errors.
- Accept `--format human|json` once, either before the command or after the complete finite command spelling.
- Reject `--format` for `run`, `dev`, help, version, and database help. Arguments after `run/dev --` remain application arguments and are not CLI options.
- Invalid format values render through human syntax failure because they cannot select JSON.
- A recognized valid JSON selection must turn later syntax failures into one JSON document with MADS204 and exit 2.
- JSON mode writes exactly one document plus newline to stdout. MADS-owned human warnings/errors do not leak to stdout or stderr in that mode; unavoidable Cargo/rustc build output stays unchanged on stderr.
- `schema_version` starts at 1. Additive fields are allowed; breaking semantic/type/removal changes require a version bump.
- Warning diagnostics occur once, only in `diagnostics`, never duplicated in command data.
- Normalize separators to `/` and make source paths package-relative when possible.
- Do not wrap `run`/`dev` streams or change application exit/signal behavior.

### Task 1: Parse output selection with command-aware failure context

**Files:**
- Modify: `crates/mads-cli/src/command.rs`
- Modify: `crates/mads-cli/src/diagnostic.rs`
- Modify: `crates/mads-cli/src/lib.rs`
- Modify: `crates/mads-cli/tests/cli.rs`

**Interfaces:**
- Produces: `OutputFormat::{Human, Json}`, `Invocation { command, format }`, and parse failures carrying optional format/canonical command.
- Reserves: `MADS204` for syntax/output-format diagnostics.

- [ ] **Step 1: Add parser tests for the complete placement matrix**

For each of `routes`, `graph`, `doctor`, and four database operations, assert
both placements parse to the same invocation. Test duplicate, missing, and
invalid format values; format rejection on stream/help/version/db-help; and a
later unknown option after valid JSON selection retaining `Json` plus canonical
command. Assert:

```rust
parse(&args(&["--format", "json", "db", "status"]))
    == Ok(Invocation::json(Command::Database(status_invocation())));
```

Also prove `mads run -- --format json` forwards the option unchanged while
`mads run --format json` is a CLI syntax error.

- [ ] **Step 2: Run parser tests against the v0.7 grammar**

```bash
cargo test -p mads-cli command::tests format
```

Expected: FAIL because the parser has no output-format model.

- [ ] **Step 3: Implement a two-phase, value-preserving parser**

Recognize at most one valid global format pair, identify the top-level and
database command, then parse command-local options. Return failure context:

```rust
pub(crate) struct ParseFailure {
    pub(crate) error: ParseError,
    pub(crate) format: Option<OutputFormat>,
    pub(crate) command: Option<CanonicalCommand>,
}
```

Use `None` format for missing/invalid format values. Keep selectors as
`OsString`-safe parsing and preserve post-separator application arguments.
Add MADS204 construction in `diagnostic.rs`; do not print from the parser.

- [ ] **Step 4: Run parser and existing CLI syntax regressions**

```bash
cargo test -p mads-cli command::tests
cargo test -p mads-cli --test cli
```

Expected: PASS with existing exit-2 behavior still human by default.

- [ ] **Step 5: Commit output-aware grammar**

```bash
git add crates/mads-cli/src/command.rs crates/mads-cli/src/diagnostic.rs crates/mads-cli/src/lib.rs crates/mads-cli/tests/cli.rs
git commit -m "feat(cli): parse finite command output formats"
```
