# MADS v0.8.0 Compiler Diagnostics Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the approved MADS-owned macro failures point to actionable user declarations with minimal generated-code noise on stable Rust and the 1.85 MSRV.

**Architecture:** Keep pure grammar/type-shape checks in each owning macro and return `syn::Error` at the smallest offending token. For constraints that require Rust trait resolution, generate one descriptively named assertion per user declaration with `quote_spanned!`; do not duplicate the same bound through router/provider construction bodies. Recognize only statically known standard route extractors and preserve rustc as the authority for custom types.

**Tech Stack:** Rust 2024, Rust 1.85 MSRV, `syn`, `quote_spanned!`, proc-macro crate-path resolution, stable/MSRV trybuild snapshots, existing controller/routes/provider/Passport macros, and the new Input/Configuration derives.

**Spec:** `docs/superpowers/specs/2026-09-06-v0.8.0-diagnostics-machine-output-design.md`

## Global Constraints

- This is Plan 5 of 8 and begins after Plans 1-4 complete their public APIs and derive diagnostics.
- Improve only constraints introduced or generated by MADS. Do not rewrite borrow checking, general Rust typing, Cargo, Diesel, native Axum, or application errors.
- Prefer `syn::Error` for syntactically knowable failures; use trait assertions only when resolution is necessary.
- Attach generated assertions to the user's type, field, import, or method span.
- Emit one root diagnostic for one root failure and suppress dependent speculative checks after an earlier malformed declaration.
- Recognize body-consuming order only for known MADS/Axum `Json`, `ValidatedJson`, and `Request` forms; custom extractors remain rustc/Axum-owned.
- Preserve accepted macro input behavior. This plan changes diagnostics, not module ownership, DI semantics, route execution, or Passport policy meaning.
- Keep separate stable/MSRV snapshots only where rustc output actually differs.
- Keep renamed `mads`, `mads-core`, and `mads-common` dependency support.

- [ ] **Step 3: Add conservative syntax-level body-consumer analysis**

name cannot prove its crate of origin and therefore remains rustc/Axum-owned;
the pass suite includes a custom bare `Json` type to prevent false positives.
