# MADS v0.8.0 Integration, Documentation, and Beta Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Integrate every approved v0.8 feature, document its exact public contracts, enforce the Linux/platform/PostgreSQL gate split, and prepare—not publish—the complete `0.8.0-beta.1` release candidate and stable-promotion checklist.

**Architecture:** Plans 1-7 remain the implementation owners. This plan adds release-level black-box acceptance evidence, current documentation, platform and PostgreSQL CI separation, packaging/release automation checks, and a single complete beta gate. Stable `0.8.0` promotes the same feature set after fixes and verification only.

**Tech Stack:** Rust 2024, Rust 1.85 MSRV, GitHub Actions Linux/macOS/Windows runners, PostgreSQL 16, Cargo feature/package/rustdoc/Clippy gates, cargo-llvm-cov, Markdown/rustdoc, and existing release scripts/workflows.

**Spec:** `docs/superpowers/specs/2026-09-06-v0.8.0-release-scope-design.md` and its five linked component specifications.

## Global Constraints

- This is Plan 8 of 8 and begins only after Plans 1-7 pass their focused gates.
- Keep the workspace at exactly `0.8.0-beta.1`; do not publish crates, push, tag, or create a GitHub release in this plan.
- Beta.1 contains every approved feature. Do not defer a missing coverage row to a later beta.
- Stable `0.8.0` may add only fixes, tests, documentation corrections, and verification—no new feature.
- Preserve ordinary Axum extractors, opt-in database mapping, explicit typed-config parsing, human CLI defaults, run/dev streams, and CLI exits.
- Linux owns complete workspace, MSRV, coverage, package, generated live-server, and real PostgreSQL gates.
- Linux/macOS/Windows own platform-sensitive parsing, JSON rendering/path normalization, atomic scaffolding, and process tests.
- Secret scanning covers errors, reports, JSON, responses, formatting, configuration, database context, and CLI output.
- Documentation must not mark a feature implemented until its acceptance test passes.
- Keep line coverage at or above 85%, missing docs denied, and unsafe code forbidden.

database structured failure data, `run/dev` format rejection, invalid project
names, and all 0/1/2 exit classes. Parse every JSON stdout as one document and
scan all channels for sentinels.
