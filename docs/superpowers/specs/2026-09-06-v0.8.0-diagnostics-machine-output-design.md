# v0.8.0 Compiler Diagnostics and Machine-Readable CLI Design

**Status:** Approved design

**Target:** MADS v0.8.0-beta.1, then v0.8.0 stable

## Context

MADS v0.7 carries structured runtime/inspection diagnostics and deterministic
human CLI rendering. Some macro-generated trait failures still surface through
opaque generated helpers or expanded Axum closures, and finite CLI commands do
not expose a supported machine format. v0.8 improves failures MADS can own and
adds one versioned JSON contract without wrapping streamed application or
compiler output.

## Goals

- Point MADS macro declaration errors at the relevant user token.
- Reduce generated-code noise for selected high-friction trait constraints.
- Cover new validation and configuration derives from their first release.
- Preserve Cargo/rustc diagnostics unchanged when MADS does not own the rule.
- Add deterministic JSON to every finite state-changing or inspection command.
- Preserve human output as the default and preserve all existing exit classes.
- Keep stdout machine-clean while retaining unavoidable Cargo/rustc stderr.

## Compiler-diagnostic boundary

v0.8 owns diagnostics for constraints introduced or generated by MADS:

- malformed `#[derive(Input)]` helper attributes;
- invalid validator parameters and validator/field type combinations;
- invalid nested/custom validation contracts;
- malformed `#[derive(Configuration)]` helper attributes;
- invalid configuration field shapes, defaults, parser signatures, key
  composition, and generated bounds;
- a controller missing one of its declared route-trait implementations;
- a non-module type named in `#[module(imports = [...])]`;
- invalid managed provider/controller dependency constraints;
- syntactically identifiable invalid MADS route signatures and known standard
  MADS/Axum extractor ordering or body-consumption violations; and
- invalid annotated Passport principal field types.

The list is intentionally not a compiler-rewriting promise. General Rust type
errors, borrow checking, application trait bounds, custom Axum extractor rules,
Diesel query typing, Cargo selection/build diagnostics, and other tool output
remain authoritative and pass through unchanged.

## Diagnostic generation strategy

Pure syntax and attribute-semantic failures use `syn::Error` at the smallest
offending token. The message states the supported form and a direct correction
when one exists.

Constraints which require Rust trait resolution use small generated assertion
items with:

- a descriptive helper name;
- the minimum necessary generic bound;
- a span attached to the user's type, field, import, or route method; and
- no unrelated generated router/controller body in the primary error path when
  stable Rust allows it.

The macro must not duplicate the same root failure through multiple assertions.
If an early malformed declaration makes a later constraint unknowable, the
later speculative diagnostic is suppressed.

Representative improvements include:

```text
Controller does not implement declared UserRoutes
NotAModule in imports does not implement Module; add #[module]
principal field `roles: u64` must be a string or supported string collection
validator `email` requires String or &str
configuration field requires parse_with or a nested Configuration type
```

Exact rustc wording can vary between stable and MSRV, so trybuild keeps
separate stable and 1.85 snapshots where the repository already follows that
pattern. The actionable subject, span, and MADS-owned explanation must remain
stable.

## Output selection syntax

The following commands accept `--format human|json`:

```text
mads new <name>
mads routes
mads graph
mads doctor
mads db generate
mads db migrate
mads db rollback
mads db status
```

Both placements are valid:

```text
mads --format json routes
mads routes --format json
mads --format json db status
mads db status --format json
```

The option appears at most once. Its default is `human`; any other value is a
syntax failure. `run`, `dev`, help, version, and database help remain
human/streaming commands and reject `--format`.

Argument parsing recognizes a valid JSON selection early enough to render
subsequent syntax errors through the JSON envelope. An invalid format value
cannot request JSON and therefore uses the ordinary human syntax diagnostic.

## Versioned JSON envelope

Every requested JSON result writes exactly one JSON document followed by one
newline to stdout:

```json
{
  "schema_version": 1,
  "command": "routes",
  "ok": true,
  "data": {},
  "diagnostics": []
}
```

Fields have these meanings:

| Field | Contract |
| --- | --- |
| `schema_version` | Integer public schema version; initially `1` |
| `command` | Canonical CLI spelling such as `new` or `db generate`; `null` when syntax cannot identify a command |
| `ok` | `true` only for exit-zero CLI-owned completion |
| `data` | Command-specific object, useful partial object, or `null` |
| `diagnostics` | Ordered MADS-owned warning/error records |

Records are serialized from structs, not hand-built text or the private child
protocol. JSON contains no ANSI escapes. Struct-field and array order is
deterministic for snapshots, but consumers must access objects by key rather
than depending on JSON object ordering.

Breaking field removal, renaming, type changes, or semantic changes require a
new `schema_version`. Fields may be added compatibly within version 1; consumers
must ignore unknown object fields. Existing fields do not silently change
meaning within one schema version.

## Diagnostic records

Each diagnostic is:

```json
{
  "severity": "error",
  "code": "MADS003",
  "title": "missing provider",
  "message": "UserService needs UserRepository",
  "subject": "UserRepository",
  "location": {
    "file": "src/app/service.rs",
    "line": 8,
    "column": 5
  },
  "suggestions": ["register UserRepository"]
}
```

`severity` is always `error` or `warning`. `subject` and `location` may be
`null`; suggestions may be empty. Existing diagnostic codes retain their v0.7
meanings. v0.8 reserves:

| Code | Meaning |
| --- | --- |
| `MADS204` | CLI syntax or output-format failure |
| `MADS230` | Project name, template, staging, or publication failure |

Migration-planning review warnings retain their existing owning diagnostic
family such as `MADS212` and use severity `warning`. They occur only in
`diagnostics`, not duplicated inside command `data`.

Messages, subjects, locations, suggestions, and nested sources follow existing
redaction rules. Arbitrary source error text is not serialized.

## Source locations

The existing location shape remains:

```json
{"file":"src/app/routes.rs","line":12,"column":5}
```

The CLI normalizes path separators to `/` and makes files relative to the
selected package root when possible. A location outside that root retains its
normalized compiler-provided form. Line and column remain one-based values
from existing metadata.

## Command data schemas

### `new`

```json
{
  "project_name": "my-app",
  "path": "my-app",
  "files": [
    "Cargo.toml",
    "mads.toml",
    "src/main.rs",
    "src/app/mod.rs",
    "src/app/routes.rs",
    "src/app/controller.rs",
    "src/app/service.rs"
  ]
}
```

Paths are normalized relative paths. Failure before atomic publication uses
`data: null`.

### `routes`

```json
{
  "routes": [
    {
      "method": "GET",
      "path": "/",
      "route_trait": "AppRoutes",
      "handler": "hello",
      "controller": "AppController",
      "location": {"file":"src/app/routes.rs","line":6,"column":5},
      "guard_active": false
    }
  ]
}
```

Ordering retains method, path, controller, route-trait, and handler ordering
from the v0.7 renderer.

### `graph`

```json
{
  "root_module": "AppModule",
  "modules": [],
  "imports": [],
  "providers": [],
  "dependencies": [],
  "construction_order": []
}
```

Items use the fields already carried by the v0.7 inspection records:

- modules: `type_name`, `namespace`, and `location`;
- imports: `importer` and `imported`;
- providers: `type_name`, optional `owner`, `origin`, `visibility`, `state`, and
  optional `location`;
- dependencies: `provider` and `dependency`; and
- construction order: provider type-name strings, or `null` when no valid plan
  can be produced.

### `doctor`

```json
{
  "checks": [
    {
      "group": "configuration",
      "status": "pass",
      "summary": "configuration sources are valid"
    }
  ]
}
```

Status values are `pass`, `skipped`, `overridden`, or `failed`. Existing group
ranking followed by summary ordering remains authoritative.

### Database commands

`db generate` returns:

```json
{
  "status": "generated",
  "migration_path": "migrations/20260906120000_schema_diff",
  "review_required": true
}
```

No-diff success uses `status: "up_to_date"`, `migration_path: null`, and
`review_required: false`. Review warnings are top-level warning diagnostics.

`db migrate` returns `{ "applied": ["version"] }`; an empty list means the
database was already current. `db rollback` returns
`{ "reverted": ["version"] }`. `db status` returns
`{ "applied": ["version"], "pending": ["version"] }`.

Migration version arrays preserve the deterministic ordering of the underlying
report.

## Failure and partial-data behavior

An invalid graph or route set retains every trustworthy inspection record in
`data`, sets `ok: false`, includes ordered error diagnostics, and exits 1. A
failure before a report exists uses `data: null`. Database and scaffolding
operational failures also use `data: null`.

A syntax error requested through a recognized `--format json` uses code
`MADS204`, `ok: false`, `data: null`, and exit 2. If no command can be
identified, `command` is `null`; otherwise it uses canonical CLI spelling.

MADS writes no human warning/error text to stdout in JSON mode. Cargo and rustc
compiler output required to build inspection targets remains unchanged on
stderr. A final MADS-owned build/inspection diagnostic still appears in the
JSON document. This is the only intentional mixed-channel case.

## Streaming commands

`mads run` and `mads dev` do not support JSON output. They continue to:

- stream Cargo/rustc output unchanged;
- stream arbitrary application stdout and stderr without interpretation;
- forward application arguments and signals;
- preserve the application exit status for `run`; and
- keep the development supervisor alive across rebuild failures.

Wrapping these byte streams in a single JSON document is outside v0.8.

## Crate boundaries

```text
crates/mads-core-macros
crates/mads-common-macros
  focused compile-time checks and assertions

crates/mads-cli/src/command.rs
  global/subcommand output selection and syntax diagnostics

crates/mads-cli/src/diagnostic.rs
  structured severity/accessors and new codes

crates/mads-cli/src/output/*
  public JSON record model and human/JSON renderer selection

crates/mads-cli/src/lib.rs
  exactly-once output and exit dispatch
```

The private application-inspection protocol remains private and versioned
independently. The CLI converts it into public JSON records instead of exposing
the wire representation directly.

## Verification

Compiler tests cover every new derive error and the selected existing opaque
cases on current stable and Rust 1.85. Pass cases cover renamed dependencies,
generic derives, feature combinations, and valid native escape hatches.

CLI tests cover:

- default human output remaining byte-for-byte stable where not intentionally
  changed;
- both valid `--format` placements, duplication, missing values, invalid
  values, and rejection by streaming/help/version commands;
- success, operational failure, syntax failure, and invalid partial inspection
  output for every finite command;
- exact schema version, canonical command spelling, `command: null`, severity,
  nullable fields, and deterministic arrays;
- path normalization on Linux, macOS, and Windows;
- one JSON document on stdout and Cargo/rustc passthrough on stderr;
- warning placement without data duplication;
- all existing and new exit codes; and
- secret/value scanning over every JSON command path.

## Acceptance criteria

1. Every approved MADS-owned compiler case produces a focused, actionable
   failure at a user declaration on stable and MSRV Rust.
2. Unrelated compiler and application diagnostics remain unmodified.
3. Every approved finite command supports the version-1 JSON envelope.
4. JSON results contain command-specific structured data, not rendered text.
5. Invalid inspection retains safe partial data; other unavailable results use
   `null`.
6. Warnings and errors have a stable severity and occur exactly once.
7. JSON stdout contains no human output, ANSI escapes, or secret values.
8. `run` and `dev` preserve their existing streaming and exit contracts.
