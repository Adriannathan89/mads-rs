# v0.8.0 Typed Configuration and Secrets Design

**Status:** Approved design

**Target:** MADS v0.8.0-beta.1, then v0.8.0 stable

## Context

`mads-core` already loads a deterministic flattened `Config` containing
source-attributed scalars, string arrays, and table presence. Conventional
`Mads::run` loads optional dotenv interpolation values, optional `mads.toml`,
and final `MADS_*` overrides. Official HTTP, database, CORS, and Passport
configuration currently parse their own fields from that store.

v0.8 adds a generic typed view over the existing loaded document. It does not
replace `Config`, introduce another loader, or change source precedence.

## Goals

- Derive typed application configuration from named structs.
- Preserve complete dotted keys and current source provenance.
- Aggregate independent missing, parsing, and validation failures.
- Support defaults, optional values, nested configuration, and custom scalar
  parsing without expanding the underlying value-shape model.
- Make secret exposure explicit and ordinary formatting safe.
- Allow explicit startup validation without global type discovery.
- Keep core free of HTTP, database, JWT, and Serde dependencies.

## Public API

`mads-core` exports:

```rust
pub type ConfigurationResult<T> =
    std::result::Result<T, ConfigurationErrors>;

pub trait Configuration: Sized {
    fn from_config(config: &Config) -> ConfigurationResult<Self>;
}

impl Config {
    pub fn parse<T: Configuration>(&self) -> ConfigurationResult<T>;
}
```

The trait method also has a hidden/documented implementation path for nested
prefix composition; callers use `Config::parse`. Applications may implement
`Configuration` manually when their shape or validation exceeds the derive
contract.

The trait and `#[derive(Configuration)]` macro are re-exported from
`mads_core`, `mads`, and `mads::prelude`. They are core APIs and require no
integration feature.

Typed failures are public structured values:

```rust
pub struct ConfigurationIssue {
    key: String,
    code: String,
    message: String,
    source: Option<String>,
}

pub struct ConfigurationErrors {
    issues: Vec<ConfigurationIssue>,
}

impl ConfigurationIssue {
    pub fn new(
        key: impl Into<String>,
        code: impl Into<String>,
        message: impl Into<String>,
    ) -> Self;

    pub fn with_source(self, source: impl Into<String>) -> Self;
    pub fn key(&self) -> &str;
    pub fn code(&self) -> &str;
    pub fn message(&self) -> &str;
    pub fn source(&self) -> Option<&str>;
}

impl ConfigurationErrors {
    pub fn from_issue(issue: ConfigurationIssue) -> Self;
    pub fn push(&mut self, issue: ConfigurationIssue);
    pub fn extend(&mut self, other: ConfigurationErrors);
    pub fn issues(&self) -> &[ConfigurationIssue];
}
```

Fields remain privately maintained behind read-only accessors so invariants and
future additive metadata do not require callers to construct invalid records.
`ConfigurationErrors::issues()` preserves declaration order. It implements
`Display` and `Error`, and `From<ConfigurationErrors> for mads_core::Error`
converts every issue into the existing aggregated `MADS020` diagnostic model.
The public constructors and ordered mutation methods let manual
`Configuration` implementations report the same structured failures as the
derive. Application-provided codes and messages are application-owned safe
text and must not contain configured values.

Example:

```rust
#[derive(Configuration)]
#[config(prefix = "app")]
struct AppConfig {
    #[config(rename = "bind_host")]
    host: String,

    #[config(default = 3000, validate(range(min = 1, max = 65535)))]
    port: u16,

    api_key: Secret<String>,
    database: DatabaseConfig,
}

let app = config.parse::<AppConfig>()?;
```

## Supported field shapes

The derive supports named structs and generic named structs whose fields fit
this matrix:

| Shape | Input representation | Parsing rule |
| --- | --- | --- |
| `String` | scalar | Preserve the complete string |
| `bool` | scalar | Rust boolean syntax |
| `char` | scalar | Exactly one Unicode scalar value |
| signed/unsigned integers | scalar | Checked parsing for the exact Rust width |
| `f32`, `f64` | scalar | Checked finite floating-point parsing |
| `PathBuf` | scalar | `Config::resolve_path` using winning-source base |
| `Option<T>` | supported scalar/nested type | `None` only when absent |
| `Secret<T>` | supported scalar type | Parse then wrap without implicit exposure |
| `Option<Secret<T>>` | scalar | Optional secret |
| `Vec<String>` | string array | Preserve element order |
| nested `Configuration` | table/descendant keys | Recursively parse composed prefix |
| `#[config(parse_with = path)]` | scalar | Invoke an application parser |

Maps, arbitrary arrays, non-string vectors, inline TOML tables, arrays of
tables, and TOML datetimes remain unsupported because the current `Config`
document cannot represent them consistently. This release does not add
environment encodings for collection values.

For `parse_with`, the callback receives `&str` and returns
`Result<FieldType, E>`. Only success/failure is consumed; MADS does not format
or retain an arbitrary parser error that might contain the input value. A
failure produces the standard safe invalid-type diagnostic with the winning
source. A parser for `Secret<T>` returns `T`, which MADS wraps only after
success.

Generic derives emit only the bounds required by their field category.
Unsupported or ambiguous generic fields require `parse_with`, a nested
`Configuration` bound, or a manual implementation; the diagnostic points at
the field.

## Key and prefix composition

Rust field names are key segments by default. `rename` replaces one field
segment. A type-level prefix is prepended at the point where that type is
parsed.

```rust
#[derive(Configuration)]
#[config(prefix = "app")]
struct AppConfig {
    #[config(rename = "bind_host")]
    host: String,             // app.bind_host
    database: DatabaseConfig, // app.database.<DatabaseConfig fields>
}
```

Nested configuration appends the outer field segment and then any prefix
declared by the nested type. Empty prefixes contribute no segment. Dots,
empty segments, duplicate field keys, and keys which collide after `rename`
are compile errors.

`Option<NestedConfig>` is `None` only when its table and all descendant scalar
or string-array keys are absent. If any descendant is present, the nested type
is parsed normally and all of its independent issues are reported. Unknown
keys are allowed because one loaded `Config` may serve multiple typed views and
official framework configuration.

## Required values and defaults

- A non-optional field is required unless it declares
  `#[config(default = ...)]`.
- An absent `Option<T>` becomes `None` and cannot also declare a default.
- `Secret<T>` cannot declare a source-code default.
- `Option<Secret<T>>` is the supported optional-secret form.
- A default must be a compatible literal for the field type.
- `default`, `parse_with`, nesting, and validation combinations are checked at
  compile time; combinations without deterministic semantics are rejected.

Defaults are evaluated without reading any source. If a validator rejects a
default, its provenance is reported as `default`. Defaults never override a
present value: a present but invalid configured value is an error rather than
a reason to fall back.

## Field validation

`#[config(validate(...))]` reuses the compatible v0.8 validator semantics:

- strings support email, nonempty, and Unicode code-point length;
- numeric fields support inclusive range, strict positive/negative, and
  multiple-of checks;
- floating-point fields reject non-finite values;
- `Vec<String>` supports nonempty and length constraints; and
- optional values validate only when present.

Configuration validation uses the same stable reason names and safe messages,
but reports through core configuration diagnostics rather than depending on
the HTTP/input issue types in `mads-common`.

Custom scalar conversion and validation can be combined in `parse_with`.
Cross-field or application/business checks remain explicit provider code or a
manual `Configuration` implementation. v0.8 does not introduce a second
cross-field callback framework in core.

## Aggregated diagnostics

`Config::parse<T>()` parses every independent field and returns no partially
constructed `T` when any issue exists. `ConfigurationErrors` and converted
diagnostics are emitted in field declaration order, recursively preserving
nested declaration order.

Each `ConfigurationIssue` contains:

- the complete dotted `key`;
- a stable `code`: `required`, `invalid_type`, or the compatible validator
  reason code;
- a safe `message`;
- the winning source label for a present value;
- `default` for a rejected default; or
- no source for a genuinely absent required value.

Conversion into `mads_core::Error` retains `MADS020`, uses the key as the
diagnostic subject, and carries the same safe reason and source attribution.

For example, a missing `app.api_key` explicitly states that the required key
was not supplied and carries no invented source. A malformed environment
override identifies `environment`; a malformed TOML winner identifies its TOML
source path. No diagnostic contains the raw or interpolated value.

Arbitrary parse errors are not inserted into the public error chain. File I/O
and source-loading failures retain the current carefully redacted behavior;
typed parsing does not weaken it.

## Secret values

`mads-core` exports:

```rust
pub struct Secret<T>(/* private */);

impl<T> Secret<T> {
    pub fn new(value: T) -> Self;
    pub fn expose(&self) -> &T;
    pub fn into_exposed(self) -> T;
}
```

The safety contract is:

- `Debug` always renders `[REDACTED]` without requiring `T: Debug`;
- `Display` always renders `[REDACTED]` without requiring `T: Display`;
- `Deref`, `AsRef`, and `Borrow` are not implemented;
- Serde `Serialize` is not implemented;
- `Clone`, `PartialEq`, and `Eq` exist only when `T` supports them; and
- configuration reports and diagnostics identify only the key and source.

`expose` and `into_exposed` are deliberate security-boundary names. The type
does not claim memory zeroization for arbitrary `T`; adding a specialized
zeroizing secret type is separate work.

## Existing loading contract

Typed parsing operates on an already loaded immutable `Config` and loads no
files or environment values. The approved exception is `PathBuf` resolution:
it preserves `Config::resolve_path`, including the current-working-directory
lookup when the winning source has no relative path base.

Conventional `Mads::run` retains this exact process-current-directory chain:

1. load optional `.env` values for interpolation only;
2. load optional `mads.toml` as the ordinary configuration document;
3. apply final scalar `MADS_*` environment overrides; and
4. allow application startup code to request typed views.

Only an entire scalar/string-array element equal to `${NAME}` is interpolated;
embedded or partial placeholders are not expanded. Process environment wins
over dotenv for interpolation. Dotenv never mutates the process environment
and never becomes a configuration source itself. A TOML value resolved through
a placeholder therefore retains the TOML file as its winning configuration
source. Direct `MADS_*` override provenance is `environment`.

Environment nesting remains unchanged:

```text
MADS_APP__HOST       -> app.host
MADS_SERVER__HOST    -> server.host
MADS_DATABASE__URL   -> database.url
```

No parent-directory or `CARGO_MANIFEST_DIR` search is added. Low-level
builders continue to load only the explicitly supplied `Config`. Existing CLI
database commands retain their separate requirement for a project
`mads.toml`.

## Explicit startup validation

Deriving `Configuration` does not register a global requirement. A reusable
type is parsed only when application code requests it. The conventional way to
make a typed view a startup requirement is a selected provider:

```rust
#[provider]
fn app_config(config: Config) -> mads::core::Result<AppConfig> {
    Ok(config.parse()?)
}
```

When the selected application graph requires this provider, parsing occurs
during construction and failure prevents lifecycle startup and listener bind.
Unused derived types do not change application startup.

## Crate boundaries

```text
crates/mads-core/src/config.rs
  Config::parse integration and provenance access

crates/mads-core/src/configuration/*
  Configuration trait, ConfigurationIssue/ConfigurationErrors,
  field parsing, aggregation, Secret<T>

crates/mads-core-macros/src/configuration.rs
  derive parsing, key composition, generated bounds, diagnostics

crates/mads/src/lib.rs
  facade and prelude re-exports
```

The implementation must not move input-validation runtime types into core or
introduce an HTTP dependency there.

## Verification

Tests cover:

- every scalar width, overflow, booleans, characters, finite floats, strings,
  and source-relative paths;
- `Vec<String>` order and scalar/array shape mismatches;
- required, default, optional, optional-secret, and nested-optional behavior;
- root and nested prefixes, rename, duplicate/colliding keys, and unknown keys;
- generic derives, `parse_with`, manual `Configuration`, and focused invalid
  signature/type diagnostics;
- compatible field validators and rejected attribute combinations;
- aggregation and deterministic nested ordering;
- structured issue accessors and lossless conversion into aggregated MADS020
  diagnostics;
- source labels for TOML, environment, defaults, and missing values;
- exact dotenv/interpolation/environment precedence regressions;
- selected-provider failure before lifecycle and bind;
- unused derived configuration causing no startup requirement;
- `Secret<T>` API, conditional traits, and absence of implicit access or
  serialization; and
- secret/value scanning across errors, diagnostics, reports, JSON, `Display`,
  and `Debug`.

Trybuild runs on stable and MSRV 1.85. Core-only tests prove the feature adds no
Axum, Diesel, JWT, or Serde dependency.

## Acceptance criteria

1. `#[derive(Configuration)]`, `Configuration`, `ConfigurationIssue`,
   `ConfigurationErrors`, `Config::parse`, and `Secret<T>` are available from
   core and the facade.
2. The approved scalar, optional, secret, string-array, nested, path, generic,
   and custom-parser matrix works without changing `Config` shapes.
3. All independent failures identify full keys and valid provenance without
   exposing values.
4. Explicit selected-provider parsing fails before lifecycle startup and bind.
5. Unused derives have no startup effect.
6. `Secret<T>` exposure is explicit and ordinary formatting is always
   redacted.
7. Conventional and low-level configuration loading retain their current
   environment and interpolation behavior.
8. Invalid derive declarations produce focused stable/MSRV diagnostics.
