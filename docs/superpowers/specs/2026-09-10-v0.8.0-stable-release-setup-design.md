# v0.8.0 Stable Release Setup Design

**Status:** Approved for repository-only preparation
**Target:** MADS.rs `0.8.0` stable on the existing `main` checkout

## Goal

Make the repository internally consistent and locally verifiable for the
stable `0.8.0` release. This work prepares source, tests, fixtures, release
automation, and stable-facing documentation; it does not push, create tags,
publish crates, or create a GitHub release.

## Current evidence

- The root workspace and seven member crates already use `0.8.0`.
- Formatting, workspace checking, Clippy, rustdoc, feature-boundary checks,
  and package-content verification pass locally.
- The release automation suite has one failure because it still asserts the
  beta workspace version.
- Several committed fixture lockfiles still contain `0.8.0-beta.1` and are
  rewritten by Cargo when stable fixtures are exercised.
- The local sandbox cannot bind a localhost socket, so the Unix dev-loop
  acceptance test cannot be validated in this environment; CI remains the
  authoritative platform check for that test.

## Design

### Stable metadata and fixtures

Keep the existing root version and exact internal dependency pins at
`0.8.0`. Promote every committed fixture `Cargo.lock` record for MADS-owned
packages to the same stable version so locked fixture builds are reproducible
and tests do not dirty the checkout.

### Release automation

Change the release-policy assertion from the beta contract to the stable
contract while retaining the temporary-fixture tests that verify beta
incrementing and stable version preparation. Update release instructions to
use the `0.8.0` example and stable tag. The script's behavior remains limited
to version metadata and Cargo validation.

### Documentation

Update stable-facing README, architecture, CLI, and example dependency pins
from beta to `0.8.0`. Preserve historical beta references in changelog
history, v0.8 feature-contract evidence, stable-promotion rationale, and
release-plan records where they describe the source beta rather than the
current stable install instructions. Ensure the stable changelog entry uses
the repository's actual release-preparation date and does not claim that
publication has already occurred.

### Verification

Run the focused release-automation suite, formatting, Clippy, locked
workspace tests and docs, feature-boundary checks, package-content policy,
and package archive generation. Run PostgreSQL and coverage gates when the
local environment provides their required services/tools. Confirm the final
diff contains only intentional stable-release changes and commit the result
on `main`.

## Alternatives considered

1. Leave beta references and only change the root version. Rejected because
   locked fixtures and stable-facing examples become inconsistent, and the
   release-policy test fails immediately.
2. Rewrite the release system or publish from this session. Rejected because
   the existing release workflow already covers publication and the approved
   scope is repository preparation only.
3. Normalize stable metadata, fixtures, policy tests, instructions, and
   stable-facing docs. Selected because it fixes the observed failure while
   preserving the existing beta history and release boundaries.

## Acceptance criteria

- No committed fixture lockfile that represents the current stable workspace
  pins MADS-owned packages to `0.8.0-beta.1`.
- The release automation suite passes against the stable workspace.
- Stable-facing installation examples use `0.8.0`.
- Release verification commands pass wherever local platform/service limits do
  not prevent them.
- No push, tag, crates.io publication, or GitHub release is performed.
