# v0.8.0 Release Scope and Coverage Design

**Status:** Implemented in 0.8.0-beta.1

**Target:** MADS v0.8.0-beta.1, then v0.8.0 stable

## Context

MADS v0.7.0 provides the Cargo-native CLI, development supervisor,
application inspection, diagnostics, and PostgreSQL migration commands. The
v0.8 milestone completes the REST and configuration usability work deferred
from that release and adds the approved `mads new <name>` minimal-project
generator.

The complete feature set ships in `0.8.0-beta.1`. Stable `0.8.0` promotes that
same feature set after defect correction, documentation review, and release
verification; stable promotion does not add work omitted from beta.1.

## Goals

v0.8 must provide:

- derived, extensible input validation which rejects invalid requests before
  handler invocation;
- structured, deterministic, source-aware validation responses;
- a complete standard REST error family and consistent MADS-owned rejection
  envelopes;
- explicit, opt-in mappings from common MADS and native Diesel results to HTTP;
- generic typed configuration over the existing source-aware `Config`;
- an explicit secret wrapper whose ordinary formatting is always redacted;
- focused diagnostics for constraints introduced by MADS macros;
- optional, versioned JSON output for finite CLI commands; and
- an offline, atomic `mads new <name>` command which creates a minimal HTTP
  application without database or authentication support.

## Architecture choice

The work extends the crates that already own each concern:

```text
mads-core
  Configuration, typed parsing, configuration diagnostics, Secret<T>

mads-core-macros
  #[derive(Configuration)]

mads-common
  Input validation contracts, validated Axum extractors, REST errors,
  opt-in Diesel-to-HTTP conversion

mads-common-macros
  #[derive(Input)] and validator diagnostics

mads-cli
  mads new, output selection, JSON records and rendering

mads
  stable facade and prelude re-exports
```

No new public validation or configuration crate is introduced. Input
validation is available with `http`; persistence conversion is available only
when both `http` and `database` are enabled. Typed configuration remains in the
framework-neutral core.

This preserves the dependency direction:

```text
mads-core-macros       mads-common-macros
        |                       |
        v                       v
    mads-core <----------- mads-common
         \                    /
          \------ mads ------/
                    |
                 mads-cli
```

## Compatibility rules

v0.8 preserves:

- ordinary Axum `Json<T>`, `Query<T>`, `Path<T>`, routers, middleware, and
  `IntoResponse` behavior;
- the current `HttpError` constructors and existing public response codes;
- explicit application control over persistence-to-delivery policies;
- the current `ConfigBuilder`, `Config`, low-level builder, and
  source-provenance APIs;
- the conventional `Mads::run` loading order and environment-key mapping;
- human-readable CLI output as the default;
- raw Cargo, rustc, and application output for `run` and `dev`; and
- CLI exit classes: zero for success, one for operational failure, and two for
  invalid syntax.

The intentional response-level change is that MADS-owned Passport and cookie
rejections join the standard JSON error envelope. Native Axum failures outside
MADS wrappers remain native.

## Release verification

Linux runs the complete formatting, Clippy, rustdoc, MSRV 1.85, workspace,
all-feature, feature-combination, package, coverage, and real PostgreSQL gates.
Linux, macOS, and Windows run platform-sensitive CLI parsing, JSON rendering,
path normalization, atomic scaffolding, and process tests. PostgreSQL
integration remains Linux-only.

Verification includes explicit secret scanning of normal output, errors,
diagnostics, reports, JSON, `Display`, and `Debug`. Tests use marker handlers,
providers, lifecycle hooks, sockets, and database operations to prove failure
happens at the required boundary without later side effects.

## Documentation and release artifacts

Design approval produces this coverage document and the five component
specifications. Implementation must then update:

- `final_timelinev1.md` and the v0.8 importance documentation;
- the README and application examples;
- CLI help/reference and JSON schema examples;
- public API rustdoc and feature tables;
- the changelog and beta release notes; and
- CI and publishing workflows for the approved gate split.

Documentation must not describe a planned component as implemented before its
acceptance tests pass.

## Explicit non-goals

v0.8 does not include:

- automatic validation of ordinary native Axum extractors;
- asynchronous or database-backed derive validators;
- full-RFC email parsing, normalization, or DNS verification;
- automatic persistence-to-HTTP conversion without `.into_http()`;
- new configuration sources, altered precedence, arbitrary TOML value shapes,
  or global discovery of derived configuration types;
- rewriting unrelated Cargo, rustc, Axum, Diesel, or application diagnostics;
- JSON wrapping for the streaming `run` or `dev` commands;
- database, JWT, cookie, or migration starter code; or
- Git initialization, dependency installation, remote templates, or additional
  code generators.

## Release acceptance

v0.8 is complete only when:

1. every coverage row has passing focused and integration evidence;
2. invalid validated input cannot invoke its handler;
3. all MADS-owned HTTP failures use the approved safe envelope;
4. configuration failures identify keys and provenance without values;
5. common database mappings are opt-in and preserve native alternatives;
6. every finite CLI command emits the approved JSON schema on request;
7. a generated minimal project compiles, inspects, runs, and serves
   `Hello World!` at `GET /` without database or JWT features;
8. the approved platform and release gates pass; and
9. `0.8.0-beta.1` contains the entire feature set promoted to stable.
