# v0.8.0 REST Errors and Diesel Mapping Design

**Status:** Implemented in 0.8.0-beta.1

**Target:** MADS v0.8.0-beta.1, then v0.8.0 stable

## Context

The current HTTP facade provides `HttpError` with bad-request, not-found,
conflict, and internal constructors. Passport and cookie extractors render
separate plain-text failures, and applications manually choose how every
database error becomes an HTTP response. v0.8 completes the standard REST
family, normalizes failures owned by MADS, and adds a deliberately opt-in
Diesel conversion extension.

## Goals

- Provide named public error types for common REST handlers.
- Preserve existing `HttpError` constructors and response codes.
- Render all MADS-owned HTTP failures with one safe JSON envelope.
- Preserve authentication challenge headers.
- Retain internal error sources without displaying or serializing them.
- Map common MADS and native Diesel result types only when the application
  explicitly requests it.
- Keep native Axum response composition and application-specific mappings
  available.

## Public error family

The `http` feature exports:

```rust
BadRequest::new(message)
Unauthorized::new(message)
Forbidden::new(message)
NotFound::new(message)
Conflict::new(message)
ValidationError::new(issues)
InternalError::new(source)
```

`ValidationError::new` accepts an iterator of `SourcedValidationIssue` values.
Input validation itself remains transport-independent; validated extractors
consume `ValidationErrors`, attach `ValidationSource::Body`, `Query`, or `Path`
to each issue, and then construct this HTTP error. Applications constructing a
validation response directly use the same explicit source attachment API.

Each named error implements `Debug`, `Display`, `Error`, and Axum
`IntoResponse`. Client-facing types accept an application-supplied message
which is treated as intentionally safe. `InternalError` accepts an error
source and has no public-message override.

Each type converts into the non-exhaustive `HttpError`, so handlers may use a
focused error or the existing mixed result alias:

```rust
async fn get_one() -> Result<Json<User>, NotFound> {
    // ...
}

async fn update() -> HttpResult<Json<User>> {
    let user = find_user()
        .await?
        .ok_or_else(|| NotFound::new("user not found"))?;
    Ok(Json(user))
}
```

The exact ergonomic conversion in generated examples uses `Into<HttpError>` or
`?` through the provided `From` implementations; callers never have to
construct internal `HttpError` variants.

These existing constructors remain source-compatible:

```rust
HttpError::bad_request(message)
HttpError::not_found(message)
HttpError::conflict(message)
HttpError::internal(source)
```

v0.8 additionally provides matching `unauthorized`, `forbidden`, and
validation construction through the named types and `HttpError` conversion.

## Status and code contract

| Public type | Status | Stable code | Message policy |
| --- | ---: | --- | --- |
| `BadRequest` | 400 | `bad_request` | Explicit safe message |
| `Unauthorized` | 401 | `unauthorized` | Explicit safe message |
| `Forbidden` | 403 | `forbidden` | Explicit safe message |
| `NotFound` | 404 | `not_found` | Explicit safe message |
| `Conflict` | 409 | `conflict` | Explicit safe message |
| `ValidationError` | 422 | `validation_error` | Fixed `input validation failed` |
| `InternalError` | 500 | `internal` | Fixed `internal server error` |

`internal` is retained rather than renamed to `internal_error` because it is
already public response behavior. All non-validation errors serialize as:

```json
{
  "error": {
    "code": "not_found",
    "message": "user not found"
  }
}
```

Validation adds the ordered `issues` array specified by the input-validation
design. No other standard type adds ad hoc top-level fields.

Responses use `application/json`. Status, code, and message are derived from
one internal response description so `Display`, `IntoResponse`, and tests do
not maintain competing mappings.

## Source and redaction policy

Standard errors may internally retain an optional source. MADS uses that path
when a safe client classification such as not-found or conflict originates in
another error. The source is available through `std::error::Error::source` for
explicit server-side handling.

`Debug` for every standard error reports only its type/code and whether a
source exists. `Display` reports only the public message. The JSON serializer
has no access to the source. Internal errors cannot accept a client message,
which prevents accidental replacement of the fixed redacted response.

Application-supplied client messages and custom validation messages remain the
application's responsibility. MADS never appends source text to them.

## MADS-owned rejection normalization

MADS-generated route responses use the standard envelope:

| Existing rejection | v0.8 response |
| --- | --- |
| Passport `Rejected` | `Unauthorized`, with `WWW-Authenticate: Bearer` |
| Passport `Forbidden` | `Forbidden` |
| Passport `Internal` | `InternalError` retaining the source |
| Cookie malformed request | `BadRequest` with `cookie request is malformed` |
| Cookie invalid response composition | `InternalError` retaining the source |
| Validated input | `ValidationError` with sourced issues |
| Validated JSON unsupported media type | 415 standard envelope |
| Validated JSON payload too large | 413 standard envelope |

The Passport Bearer challenge remains present only on authentication rejection;
forbidden and internal responses do not add it. A manually constructed
`Unauthorized` has no implicit authentication scheme. Passport uses an
internal header-aware conversion rather than making every 401 response claim
Bearer authentication.

MADS-owned rejection messages are fixed:

| Rejection | Client message |
| --- | --- |
| Passport rejected | `authentication was rejected` |
| Passport forbidden | `access was denied` |
| Cookie malformed request | `cookie request is malformed` |
| Validated JSON unsupported media type | `content type must be application/json` |
| Validated JSON payload too large | `request body is too large` |
| Other client-class validated body read failure | `request body could not be read` |
| Any server-class failure | `internal server error` |

These strings are the complete client messages. MADS does not append native
extractor, Passport, cookie, or source-error text.

Ordinary Axum extractors, native routes, custom middleware, and arbitrary
`IntoResponse` types are not normalized. This preserves the established
escape hatch.

## Opt-in Diesel conversion

When both `http` and `database` are enabled, `mads-common` exports:

```rust
pub trait IntoHttpResult<T> {
    fn into_http(self) -> HttpResult<T>;
}
```

The facade and prelude re-export the trait. Implementations cover:

```rust
Result<T, DatabaseError>
diesel::QueryResult<T>
```

This supports both the managed database boundary and deliberate native Diesel:

```rust
let user = database
    .run(move |connection| query.first(connection))
    .await
    .into_http()?;

let user = query.get_result(connection).into_http()?;
```

There is intentionally no blanket `From<DatabaseError> for HttpError` and no
automatic route-level conversion. The method call is the application's policy
choice.

## Database classification

The mapper examines a MADS `DatabaseError` and, for its query variant, the
underlying Diesel error. Native `QueryResult` uses the same classifier.

| Diesel/MADS failure | HTTP result |
| --- | --- |
| `diesel::result::Error::NotFound` | 404 `not_found`, `resource not found` |
| Database unique-constraint violation | 409 `conflict`, `resource already exists` |
| Configuration | 500 `internal`, fixed message |
| Pool acquisition | 500 `internal`, fixed message |
| Blocking interaction | 500 `internal`, fixed message |
| Migration | 500 `internal`, fixed message |
| Foreign-key, check, not-null, serialization, rollback, and all other query errors | 500 `internal`, fixed message |

Only Diesel's typed unique-violation classification triggers conflict. MADS
does not parse backend error strings or constraint names. The originating
`DatabaseError` or Diesel error remains the standard error's private source,
including for mapped not-found and conflict responses.

The mapper never serializes or formats database URLs, SQL, bound values,
constraint names, table names, column names, or server messages. Applications
which need a safe domain-specific 404/409 message use `map_err` instead of the
standard mapper. Diesel's `OptionalExtension` remains the normal way to turn
not-found into `Option<T>` before delivery mapping.

## Crate boundaries and features

```text
crates/mads-common/src/response.rs
  standard errors, envelope, conversion, redaction

crates/mads-common/src/passport/error.rs
  Passport-to-standard response mapping

crates/mads-common/src/cookie.rs
  cookie-to-standard response mapping

crates/mads-common/src/database/http.rs
  IntoHttpResult and Diesel classification

crates/mads/src/lib.rs
  feature-correct facade/prelude exports
```

The standard REST family and validation error require only `http`.
`IntoHttpResult` appears only with `http + database`. Database-only and
core-only builds gain no HTTP dependency. JWT-only remains free of Axum unless
`http` is selected, matching existing feature boundaries.

## Verification

Tests cover:

- the exact status, content type, code, and message for every standard type;
- direct named-error handlers and mixed `HttpResult` handlers;
- compatibility of all existing `HttpError` constructors;
- validation issues as the sole envelope extension;
- source retention plus `Display`, `Debug`, response, and serialization
  redaction;
- Passport rejected/forbidden/internal responses and the exact Bearer header;
- cookie request/response errors without cookie data exposure;
- ordinary native Axum responses remaining unchanged;
- MADS `DatabaseResult` and native `QueryResult` extension methods;
- real PostgreSQL not-found and named unique-constraint violations;
- safe 500 mapping for every other `DatabaseErrorKind` and representative
  Diesel database errors;
- absence of implicit `From<DatabaseError> for HttpError`; and
- core-only, HTTP-only, database-only, `http + database`, JWT-only, and
  all-feature builds.

Real PostgreSQL evidence runs on Linux. Pure classification and feature tests
run in the ordinary workspace/platform matrix.

## Acceptance criteria

1. All seven standard errors are public through `mads-common` and `mads` with
   the required features.
2. Existing error constructors and public codes remain compatible.
3. MADS-owned validation, Passport, cookie, and JSON transport failures use a
   consistent JSON envelope.
4. Passport authentication rejection retains `WWW-Authenticate: Bearer`.
5. Internal details and database context never enter client-visible or ordinary
   formatting output.
6. `.into_http()` works for both approved result types and performs only the
   approved 404/409/500 classification.
7. Database conversion remains explicitly opt-in.
8. Applications can still return arbitrary native Axum responses and implement
   custom database delivery policy.
