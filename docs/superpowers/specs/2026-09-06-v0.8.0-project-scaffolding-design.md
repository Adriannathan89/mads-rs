# v0.8.0 Project Scaffolding Design

**Status:** Implemented in 0.8.0-beta.1

**Target:** MADS v0.8.0-beta.1, then v0.8.0 stable

## Release scope

This component adds `mads new <name>` with its tests and documentation. It is
one part of the complete v0.8.0 release, which also includes input validation,
structured validation responses, the expanded REST error model, opt-in
Diesel-to-HTTP error mapping, typed configuration and secret-safe values,
improved compiler diagnostics, and machine-readable CLI output. Those features
will be defined in companion specifications.

The full release scope was explicitly confirmed after a coverage review
against `final_timelinev1.md`. Existing commands retain their contracts.
Publishing, tagging, and promoting release branches are separate release
operations. The release-level matrix is defined in
[`2026-09-06-v0.8.0-release-scope-design.md`](2026-09-06-v0.8.0-release-scope-design.md).

## Approved application layout

The command creates the following seven files:

```text
<name>/
├── Cargo.toml
├── mads.toml
└── src/
    ├── main.rs
    └── app/
        ├── mod.rs
        ├── routes.rs
        ├── controller.rs
        └── service.rs
```

`src/app/mod.rs` declares `AppModule` and the ordinary Rust source modules.
`AppRoutes` declares `GET /`. `AppController` implements that contract and
depends on `AppService`, which supplies the plain-text `Hello World!` response.
These declarations share the `crate::app` namespace and belong to `AppModule`.

`src/main.rs` uses the standard `#[mads::main]` entry point and
`Mads::run::<AppModule>().await`. The application therefore participates in
normal `mads run`, `mads dev`, `mads routes`, `mads graph`, and `mads doctor`
behavior.

The generated MADS dependency disables default features and enables only
`http` and `runtime-tokio`. Database and JWT dependencies and their
configuration, schemas, migrations, and authentication code are absent.

## Generated manifest and configuration

The generated package manifest is equivalent to:

```toml
[package]
name = "<name>"
version = "0.1.0"
edition = "2024"
rust-version = "1.85"

[dependencies]
mads = { version = "=<installed-cli-version>", default-features = false, features = ["http", "runtime-tokio"] }
```

The dependency is exact. A `0.8.0-beta.1` CLI generates
`=0.8.0-beta.1`; stable `0.8.0` generates `=0.8.0`. The application package's
own initial version remains the independent Cargo convention `0.1.0`.

The generated `mads.toml` is:

```toml
[server]
host = "127.0.0.1"
port = 3000
```

Conventional runtime overrides continue to use the existing configuration
mapping: `MADS_SERVER__HOST` maps to `server.host` and
`MADS_SERVER__PORT` maps to `server.port`.

## Generated source contract

The templates compile to this dependency flow:

```text
main -> AppModule -> AppController -> AppService
                         |
                         +-> implements AppRoutes -> GET /
```

`src/app/mod.rs` declares its three ordinary submodules and the unit
`#[module] pub struct AppModule`. `src/app/routes.rs` declares the public route
trait, `src/app/controller.rs` declares and implements its managed controller,
and `src/app/service.rs` declares the managed service. The service owns the
literal `Hello World!`; the controller delegates rather than duplicating the
response.

## Approved command behavior

`mads new my-app` creates `./my-app` relative to the invocation directory.
An existing destination is rejected, including an empty directory. The command
generates files without downloading dependencies, building the application, or
initializing Git. It prints the next steps:

```text
cd my-app
mads dev
```

The name must start with lowercase ASCII and its remaining characters may be
lowercase ASCII, digits, `-`, or `_`. Rust keywords and Cargo-reserved package
names are rejected rather than rewritten. The directory and package spelling
remain exactly as supplied. Cargo's ordinary hyphen-to-underscore crate-name
mapping is not duplicated by the generator.

The reserved-name contract is frozen to Cargo 1.85 package-name validation and
the Rust 2024 keyword set. Tests enumerate that fixed set so behavior does not
silently change with the Cargo executable used to build or run MADS. The
generator implements the checks internally and does not invoke `cargo new`.

## Proposed implementation

Bundle the starter templates in `mads-cli` so generation can run outside an
existing Cargo project and without network access. Extend the existing parser,
command dispatcher, and help output. Keep name validation, template rendering,
and filesystem creation in a focused scaffolding module.

Bundled templates fit the approved command behavior. Delegating to `cargo new`
would introduce Cargo initialization behavior and possible parent-workspace
changes; downloading a remote starter would introduce a network requirement.
Neither is necessary for this fixed starter.

Use the existing CLI exit classes: success returns 0, invalid command syntax or
name returns 2, and operational filesystem failures return 1. Validate all
arguments before creating a staging directory. Render and write all seven files
into a private sibling staging directory, then publish it with one atomic rename.
If the destination appears before publication, fail without changing it.
Failure cleanup removes only the private staging directory and preserves every
pre-existing file, directory, and symlink.

No `--template`, `--database`, `--jwt`, `--vcs`, interactive prompt, or target
directory option is introduced in v0.8.

## Output contracts

Human success output identifies the created relative path and prints only the
two next steps shown above. Human failure output uses the ordinary CLI
diagnostic renderer.

With `--format json`, success uses the v0.8 versioned envelope and returns:

```json
{
  "schema_version": 1,
  "command": "new",
  "ok": true,
  "data": {
    "project_name": "my-app",
    "path": "my-app",
    "files": [
      "Cargo.toml",
      "mads.toml",
      "src/main.rs",
      "src/app/mod.rs",
      "src/app/routes.rs",
      "src/app/controller.rs",
      "src/app/service.rs"
    ]
  },
  "diagnostics": []
}
```

The files remain in the documented deterministic order. Syntax failures use
exit 2; operational failures use exit 1 and `data: null`. Scaffold failures use
a new stable CLI diagnostic category without reusing an existing v0.7 code.

## Verification design

Focused CLI tests will cover generation outside a Cargo project, the exact
seven-file layout, accepted names, invalid arguments and names, help output,
existing destinations, and preservation of unrelated files. Filesystem tests
will exercise failures, dangling and ordinary symlinks, and destination races
during creation.

A generated consumer will be compiled against the local MADS facade through a
test-only dependency substitution. Its dependency metadata must show HTTP and
Tokio without database or JWT. Acceptance checks will verify `GET /` returns
`Hello World!` and that standard inspection commands recognize the application.

After focused tests, run the repository's formatting, Clippy, workspace tests,
rustdoc, MSRV, feature, package, and coverage checks. Platform-sensitive
generation and path tests run on Linux, macOS, and Windows; the complete gate
and generated live HTTP test run on Linux. Update the CLI reference, current
architecture and roadmap, and release notes to describe the confirmed scope.

## Acceptance criteria

1. A valid invocation creates exactly the seven documented files beneath one
   previously absent child directory.
2. The manifest uses package version `0.1.0`, edition 2024, MSRV 1.85, and the
   exact installed MADS version with only HTTP and Tokio runtime features.
3. Existing destinations and invalid names cause no modifications.
4. Interrupted or failed generation leaves no published partial project.
5. Generation performs no network, Cargo build, dependency resolution, or Git
   operation.
6. The generated application compiles, passes `mads routes`, `mads graph`, and
   `mads doctor`, and returns plain `Hello World!` from `GET /`.
7. Human and JSON output obey their approved schemas and exit classes.
