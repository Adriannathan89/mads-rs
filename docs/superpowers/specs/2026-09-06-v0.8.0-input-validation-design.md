# v0.8.0 Input Validation Design

**Status:** Approved design

**Target:** MADS v0.8.0-beta.1, then v0.8.0 stable

## Context

MADS currently re-exports Axum's `Json<T>`, `Query<T>`, and `Path<T>` without a
framework validation contract. Applications must deserialize first and perform
their own checks inside a handler or service. v0.8 adds an explicit validated
extractor family and the approved derive API:

```rust
#[derive(serde::Deserialize, Input)]
struct CreateUser {
    #[validate(email)]
    email: String,
}
```

The design takes Zod's schema and issue model as a usability reference. It does
not attempt to reproduce JavaScript coercion, transformations, or every Zod
format.

## Goals

- Keep `#[derive(Input)]` as the primary validation API.
- Validate body, query, and path inputs before a route handler runs.
- Cover Rust primitive types, strings, options, structs, enums, tuples,
  sequential collections, and standard string-keyed maps.
- Provide deterministic, source-aware, client-mappable issues.
- Collect every independent validator issue after deserialization.
- Support field-level, whole-value, nested, and fully manual validation.
- Retain ordinary Axum extractors as unchanged escape hatches.
- Emit focused compile diagnostics for invalid declarations.

## Public traits and values

`mads-common` owns:

```rust
pub trait Input {
    fn validate(&self) -> ValidationResult;
}

pub type ValidationResult = Result<(), ValidationErrors>;

pub enum ValidationPathSegment {
    Field(String),
    Index(usize),
}

pub enum ValidationSource {
    Body,
    Query,
    Path,
}

pub struct SourcedValidationIssue {
    source: ValidationSource,
    issue: ValidationIssue,
}
```

`ValidationErrors` is a non-empty-capable ordered collection of
`ValidationIssue`. An issue has a relative path, stable code, and safe message.
Paths consist of string field/map segments and numeric collection segments.
Input validation itself is transport-independent, so source attribution is
added only when an extractor converts the errors into an HTTP
`ValidationError`.

The public construction surface supports application validation without
requiring private fields:

```rust
ValidationIssue::custom("invalid_username", "username is not allowed")
    .at_field("username")
ValidationErrors::from_issue(issue)
errors.push(issue)
errors.extend(other)
errors.issues()
errors.into_issues()
```

`ValidationIssue::at_field` and `ValidationIssue::at_index` append one segment
to the issue's current relative path, so application validators can construct a
path in request order. `ValidationIssue::path`, `code`, and `message` expose
read-only views. Derive-generated nesting prefixes its external field, variant,
map-key, or collection-index segment ahead of the path returned by a nested or
field callback. `ValidationPathSegment` is public and has `Field(String)` and
`Index(usize)` variants.

`ValidationIssue::with_source(ValidationSource)` consumes an unsourced issue
and returns `SourcedValidationIssue`. `ValidationErrors::into_issues` consumes
the collection without changing order. `SourcedValidationIssue` exposes
read-only `source`, `path`, `code`, and `message` accessors. Its source enum
serializes through the HTTP error envelope as `body`, `query`, or `path`.
Validated extractors attach that source automatically. Applications manually
constructing a `ValidationError` must attach it explicitly, so a serialized
validation issue can never have missing or invented provenance.

Constructors never require or store a rejected value. Built-in issues do not
echo values. Applications are responsible for keeping their own custom codes
and messages safe.

`Input` and its derive macro are re-exported from:

- `mads_common::Input`;
- `mads::Input`; and
- `mads::prelude::Input`.

The trait and derive use Rust's separate type and macro namespaces, matching
the normal Serde derive experience.

## Derive forms

Named, tuple, and unit structs plus all enum variant forms are supported.
Generic structs and enums receive only the bounds required by their annotated
fields. Const-generic arrays retain their declared length. A borrowed value may
implement and invoke `Input` directly, but HTTP extractors require an owned
Serde `DeserializeOwned` value.

Validators may be grouped or repeated and execute in lexical source order:

```rust
#[derive(serde::Deserialize, Input)]
#[validate(custom = validate_passwords)]
struct CreateUser {
    #[validate(email, length(max = 254))]
    email: String,

    #[validate(length(min = 8))]
    password: String,

    #[validate(required)]
    nickname: Option<String>,
}
```

The derive performs validation only. Serde remains responsible for constructing
the Rust value, including aliases, defaults, custom deserializers, tagging,
flattening, denial of unknown fields, and other Serde behavior.

## Built-in validator matrix

| Validator | Supported field shape | Rule |
| --- | --- | --- |
| `email` | `String`, `&str` | Zod-default practical email syntax |
| `length(min = N)` | strings and supported collections | Length is at least `N` |
| `length(max = N)` | strings and supported collections | Length is at most `N` |
| `length(min = A, max = B)` | strings and supported collections | Inclusive bounds |
| `length(exact = N)` | strings and supported collections | Length equals `N` |
| `nonempty` | strings and supported collections | Length is greater than zero |
| `range(min = A)` | all integers and floats | Value is at least `A` |
| `range(max = B)` | all integers and floats | Value is at most `B` |
| `range(min = A, max = B)` | all integers and floats | Inclusive bounds |
| `positive` | all integers and floats | Value is strictly greater than zero |
| `negative` | all signed integers and floats | Value is strictly less than zero |
| `multiple_of = N` | all integers and floats | Value is a multiple of nonzero `N` |
| `required` | `Option<T>` | Value must be `Some` |
| `nested` | nested input or supported collection | Recursively invoke `Input` |
| `custom = path` | any field or complete derived value | Invoke application validator |

Supported automatic collection shapes are `Vec<T>`, `[T; N]`, tuples,
`HashMap<String, T>`, and `BTreeMap<String, T>`. Length validation does not
implicitly validate elements; `nested` opts into recursive element validation.
Other collection and map-key types use custom validation or a manual `Input`
implementation.

Primitive values also implement `Input`: `f32` and `f64` reject non-finite
values, while integers, booleans, characters, and strings have no intrinsic
constraints. Therefore `#[validate(nested)]` supports primitive collections
such as `Vec<f64>` and reports non-finite elements at their numeric indices.
This primitive-element behavior was explicitly approved during implementation.

String length uses Unicode scalar-value/code-point count, not UTF-8 bytes or
grapheme clusters. Email validation uses the unmodified string, the practical
default Zod syntax policy, and no trimming, normalization, RFC-completeness
claim, or DNS lookup.

Numeric range bounds are inclusive. `positive` and `negative` are strict.
Derived `f32` and `f64` fields reject `NaN` and either infinity before their
declared numeric validators run. Integer multiples are exact; floating-point
multiples use tolerance derived from decimal precision rather than a raw
remainder equality check.

`Option<T>` skips all value validators when it is `None`, except `required`.
When it is `Some`, validators apply to the contained value. `required` on a
non-option, `negative` on an unsigned integer, contradictory/exact length
forms, a minimum above its maximum, and a zero multiple are compile failures.

## Custom and manual validation

Field-level and complete-value callbacks are synchronous and use the same
multi-issue result as `Input`:

```rust
fn validate_username(value: &str) -> ValidationResult {
    // Return Ok(()) or one/more relative ValidationIssue values.
}

fn validate_passwords(input: &CreateUser) -> ValidationResult {
    // Cross-field validation with paths relative to CreateUser.
}
```

A field callback receives a reference compatible with the field value. The
derive prefixes each returned issue path with that field's external path. A
struct/enum callback receives `&Self`; its issue paths are already relative to
that value's root. Callbacks run synchronously. Database-backed and other async
business validation belongs in the handler or service.

Applications that need complete control implement the trait instead of using
the derive:

```rust
impl Input for CreateUser {
    fn validate(&self) -> ValidationResult {
        // Application-owned validation.
    }
}
```

The validated extractors depend only on `Input`, so derived, mixed, and manual
implementations behave identically at the request boundary.

## Deterministic traversal and paths

After successful deserialization, issues are collected in this order:

1. fields in declaration order;
2. validators on a field in lexical attribute order;
3. nested sequential values by numeric index;
4. nested `HashMap<String, T>` and `BTreeMap<String, T>` values by lexical key;
5. whole-struct or whole-enum custom validators after field traversal.

Issue paths follow the request wire representation, not necessarily the Rust
identifier:

- Serde `rename` and `rename_all` use their external names;
- a flattened field does not add its Rust container field name;
- a default externally tagged enum adds the external variant name;
- an internally tagged enum adds no variant segment;
- an adjacently tagged enum adds the configured content-field segment;
- an untagged enum adds no variant segment;
- renamed variants and fields use their external names; and
- tuple/tuple-variant fields use numeric indices.

For example, a nested issue can serialize as:

```json
{
  "source": "body",
  "path": ["users", 0, "email"],
  "code": "invalid_format",
  "message": "invalid email address"
}
```

## Issue codes

The built-in stable code set is:

| Code | Meaning |
| --- | --- |
| `required` | A required field or option is absent/null |
| `invalid_type` | Serde cannot convert a value to the required Rust type, or a float is non-finite |
| `invalid_syntax` | The request representation is malformed |
| `invalid_format` | Email or another future format validator fails |
| `too_small` | A numeric or length minimum fails |
| `too_big` | A numeric or length maximum fails |
| `not_multiple_of` | A numeric multiple constraint fails |
| `custom` | Default code for an application callback |

Custom validators may provide their own stable code. Exact-length failure uses
`too_small` or `too_big` according to the observed direction. `nonempty` uses
`too_small`.

Built-in client messages are frozen as follows:

| Code or validator | Message |
| --- | --- |
| `required` | `required value is missing` |
| `invalid_type` | `input has an invalid type` |
| `invalid_syntax` | `input syntax is invalid` |
| failed `email` | `invalid email address` |
| `too_small` | `value is too small` |
| `too_big` | `value is too big` |
| `not_multiple_of` | `value is not a multiple of the required number` |

The messages do not interpolate the rejected value. Custom codes and messages
remain application-owned safe text.

## Validated HTTP extractors

The `http` feature exports:

```rust
ValidatedJson<T>
ValidatedQuery<T>
ValidatedPath<T>
```

Each wrapper implements the corresponding Axum extraction contract for
`T: DeserializeOwned + Input`. On success the wrapper exposes the typed value
through tuple destructuring and `into_inner`, matching the ordinary extractor
experience.

The runtime sequence is strict:

```text
read request representation
  -> Serde deserialize T
  -> T::validate()
  -> attach body/query/path source to issues
  -> invoke handler only when no issues exist
```

Serde deserialization is fail-fast and may therefore return only its first
conversion issue. Once a typed value exists, MADS collects every independent
built-in, nested, and custom issue. Replacing Serde with a second schema parser
is explicitly outside v0.8 because it would diverge from custom Serde behavior.

Unknown fields retain normal Serde semantics: ignored by default and rejected
only when the type opts into `#[serde(deny_unknown_fields)]`.

## HTTP response contract

Validation sources serialize as `body`, `query`, or `path`. Syntax, type,
required-field, and validator failures from the validated extractor family all
return status 422:

```json
{
  "error": {
    "code": "validation_error",
    "message": "input validation failed",
    "issues": [
      {
        "source": "body",
        "path": ["email"],
        "code": "invalid_format",
        "message": "invalid email address"
      }
    ]
  }
}
```

The envelope contains no rejected value. Built-in messages are fixed English
messages in v0.8.

JSON failures outside schema conversion preserve transport semantics while
joining the standard envelope:

- missing or unsupported content type returns 415 with
  `unsupported_media_type` and `content type must be application/json`;
- configured body limit overflow returns 413 with `payload_too_large` and
  `request body is too large`; and
- other body-read failures preserve a client-class Axum status as safe 400
  `bad_request` with `request body could not be read`, while an Axum
  server-class failure becomes redacted 500 `internal` with
  `internal server error`.

These transport errors do not contain `issues`. Query and path representation
syntax failures are validation errors with their corresponding source.

Ordinary `Json<T>`, `Query<T>`, and `Path<T>` remain the native Axum re-exports
and do not invoke `Input`. This compatibility escape hatch is deliberate.

## Macro diagnostics

The derive rejects unknown, duplicate, contradictory, or malformed attributes
at their source span. It also provides focused checks for:

- validators applied to incompatible field shapes;
- invalid or overflowing literal parameters;
- invalid range and length relationships;
- unsupported automatic collection/map shapes;
- missing `Input` bounds for `nested`; and
- custom callbacks with the wrong input or return type.

Serde attributes that influence external paths are parsed only to calculate
issue paths; Serde remains authoritative for actual deserialization.

## Crate boundaries and features

```text
crates/mads-common/src/validation/*
  Input, issues, paths, sources, validated extractors

crates/mads-common-macros/src/input.rs
  derive parsing, code generation, focused diagnostics

crates/mads-common/src/response.rs
  ValidationError envelope integration

crates/mads/src/lib.rs
  facade and prelude re-exports under http
```

Validation adds no database, JWT, or cookie dependency. The minimal generated
project receives the API through its `http` feature.

## Verification

Tests cover:

- every compatible validator/type pair and every rejected pairing;
- all integer widths, both float widths, finite and non-finite values;
- Unicode code-point length and frozen accepted/rejected email vectors;
- option absence/presence and combined validators;
- nested structs, every enum representation, tuples, arrays, vectors, and
  deterministic string-keyed maps;
- Serde rename, rename-all, flatten, defaults, aliases, and unknown fields;
- generic derives and focused missing-bound diagnostics;
- one and multiple custom issues plus a manual `Input` implementation;
- body/query/path success and rejection snapshots;
- first-only Serde conversion failure versus all post-conversion issues;
- 413, 415, and body read failures;
- ordinary Axum extractor behavior remaining unchanged; and
- a handler invocation counter proving invalid input never reaches the handler.

Trybuild runs on stable and MSRV 1.85. HTTP tests exercise generated MADS routes
and native Axum composition.

## Acceptance criteria

1. `#[derive(Input)]` is available through `mads-common`, the facade root, and
   the prelude with `http` enabled.
2. The approved primitive, string, numeric, option, nested, collection, enum,
   generic, and custom matrix works with deterministic issues.
3. Invalid validated input never invokes the route handler.
4. Body, query, and path errors use the approved source-aware 422 schema.
5. Transport failures preserve 413/415 semantics without leaving the standard
   error envelope.
6. Built-in failures and diagnostics never echo rejected input.
7. Ordinary Axum extractors remain available and unmodified.
8. Invalid macro declarations fail at actionable user spans on stable and
   MSRV Rust.
