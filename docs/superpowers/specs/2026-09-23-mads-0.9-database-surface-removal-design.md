# MADS.rs 0.9 Database Surface Removal Design

Status: draft for written review; design sections approved in conversation.

This spec updates the in-progress MADS 0.9 persistence work. It supersedes
the Diesel-retention and CLI-0.8 decisions in
`2026-09-23-mads-persistence-design.md`, the implementation plan derived from
that spec, and corresponding statements in `docs/mads-persistence.md`.
Existing feature-branch commits through `bcfd262` remain the implementation
baseline. This change completes on that branch with native, inline execution
and minimal refactoring outside the affected boundaries.

## Intended outcome

MADS 0.9 has one supported framework database path: applications add
`mads-persistence` with `sea-orm-postgres` and explicitly import its global
`DatabaseModule`. Repositories and services receive the native SeaORM
`DatabaseConnection`. `mads` does not activate persistence automatically.

The Diesel integration and migration CLI leave the current public product
surface. All framework crates and `mads-cli` release as version 0.9.0. The CLI
follows `workspace.package.version` in later releases.

## Crate boundaries and public API

- Remove `mads-common`'s `database` feature, `database` module, Diesel and
  deadpool dependencies, database re-exports, auto-configuration, migration
  extension, and `IntoHttpResult` mapping for Diesel results. Keep HTTP,
  validation, JWT, cookies, logger, and other non-database behavior intact.
- Remove the `mads` facade's `database` feature, native Diesel re-exports,
  database prelude exports, and the `http + database` conversion. Its default
  feature set is HTTP, logger, and Tokio runtime. Its `common` compatibility
  aggregate remains available for HTTP and logger but carries no persistence.
- Remove workspace Diesel, Diesel migrations, deadpool-Diesel, and
  `diesel_table_macro_syntax` dependencies after all consumers are removed.
  The ordinary `mads`, `mads-common`, and `mads-cli` dependency trees must not
  contain Diesel or libpq. The opt-in `mads-persistence` feature continues to
  select SeaORM's PostgreSQL SQLx driver and Tokio/Rustls runtime.
- Preserve `mads-core`'s ordinary provider API and new optional lifecycle
  constructor contract. Do not replace SeaORM with a MADS database wrapper,
  add migrations to `mads-persistence`, or add automatic HTTP conversion.

Removing the old public features and types is an intentional 0.9 source
compatibility break. Applications using Diesel must migrate their own database
layer or choose the native SeaORM connector. MADS 0.9 supplies no compatibility
shim or automatic migration.

## CLI behavior and version policy

- Remove `mads db generate`, `migrate`, `rollback`, and `status`, including the
  `db` command group, parser branches, help text, implementation modules,
  database-specific output records, diagnostics, and public JSON data types.
  `mads db` and `mads db ...` are unknown top-level commands with syntax exit
  code 2, using the ordinary CLI error formatting rules.
- Keep `mads new`, `run`, `dev`, `routes`, `graph`, and `doctor`, including their
  existing human and JSON behavior. The scaffold pins framework 0.9.0 and the
  CLI's inspection compatibility check uses the actual `mads` dependency
  version, not the CLI package version.
- Change `mads-cli` from literal `version = "0.8.0"` to
  `version.workspace = true`. Its exact internal framework pins remain at
  0.9.0. Remove the release script's `--keep-cli-version` exception and its
  tests so later releases update CLI and framework together.
- Publish `mads-cli` 0.9.0 in both beta and stable workflows after every
  framework crate, including `mads-persistence`. Preserve each workflow's
  existing protected environment, package verification, retry policy where
  present, and release-tag behavior.

## Tests, CI, and documentation

- Remove code, test files, example fixtures, and migration fixtures that exist
  only to exercise the retired Diesel or `mads db` path. Retain shared tests
  for core lifecycle, configuration, HTTP, CLI execution, and inspection.
  Update mixed tests to cover their surviving behavior instead of deleting
  unrelated assertions.
- Keep PostgreSQL 16 CI service and ignored acceptance tests for
  `mads-persistence`: native CRUD, transactions, readiness, safe error chains,
  close after query failure, shutdown order, and conventional startup.
  Remove Diesel/CLI database PostgreSQL gates and libpq installation steps.
- Verify default and no-feature dependency trees omit Diesel/libpq; verify
  `mads db` rejection, CLI version 0.9.0, scaffold version 0.9.0, and surviving
  HTTP/JWT/cookie behavior. Run formatting, Clippy, workspace tests/docs,
  package contents, SeaORM 2.0.0 lower-bound tests, PostgreSQL acceptance,
  and the existing coverage gate.
- Update active root and crate READMEs, `docs/CLI.md`,
  `docs/ARCHITECTURE.md`, `docs/mads-persistence.md`, release workflows, and
  changelog to describe the 0.9 contract. Keep historical 0.8 documents as
  archival records, not current recommendations. Mark the older persistence
  spec and plan as superseded where their release assumptions conflict.

## Error and lifecycle behavior

The already implemented persistence error surface remains: `MADS140`,
`PersistenceErrorKind`, safe `Display`/`Debug`, and retained typed sources.
The factory still returns either a connector-native database instance or a
typed persistence error. The imported `DatabaseModule` still contributes one
native provider; its infrastructure hook pings before serving and calls
`close_by_ref()` during graceful shutdown. Ordinary providers and the
framework's existing rollback and reverse-shutdown behavior remain intact.
There is no automatic mapping from SeaORM errors to HTTP responses.
