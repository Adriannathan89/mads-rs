# MADS full-testing report — 2026-09-25

Dependency follow-up: the workspace lockfile was subsequently updated to `time 0.3.47`; `cargo audit` no longer reports RUSTSEC-2026-0009. `rsa 0.9.10` remains because RustSec lists no patched release or newer stable release. The results below describe the original testing snapshot unless explicitly noted.

Scope: `docs/MADS_FULL_TESTING.md`, branch `main` at `165fff2e56b277f55ecb3948feae8149c0183e95`, MADS 0.9.1, Linux x86_64, Rust 1.96.0. Live probes used loopback HTTP/1.1 and disposable PostgreSQL 16. Results below are limited to the specified workloads; a pass does not establish universal security or production readiness.

## Outcome

- `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`: pass.
- `cargo test --workspace --all-features --locked --quiet`: pass, including integration and doctests (some tests are intentionally ignored).
- `cargo audit` (current RustSec database, 343 lockfile dependencies): **fails with two advisories**. `time 0.3.36` is affected by RUSTSEC-2026-0009; its patched release is 0.3.47. `rsa 0.9.10` is affected by RUSTSEC-2023-0071, for which RustSec lists no patched release. See [the dependency issue](issues/2026-09-25-time-advisory.md). The RSA advisory concerns private-key operations with observable timing; MADS exposes RSA JWT signing and verification, but this run did not establish an exploitable JWT path. Do not equate lockfile presence with proven exploitability.
- Attribution follow-up: `time` is transitive through `cookie` and `simple_asn1`; their inspected date parsers use fixed HTTP-date/ASN.1 formats, not the RFC 2822 form required by that advisory. The vulnerable version is selected by this workspace lockfile, not forced by MADS manifest constraints on every library consumer. `rsa` is transitive through `jsonwebtoken`; its inspected JWT path signs with a private key and verifies with a public key, whereas the Marvin advisory concerns private-key recovery from a timing oracle. Neither audit finding was reproduced as an exploitable MADS request path.
- Existing benchmark harness: 13 tests passed or expected-skipped (10 passed, 3 skipped) with loopback permission.
- HTTP smoke workloads: hello 200/200, connection churn 40/40, validation 90/90, oversized 4/4, aborted upload 32/32, JWT 90/90. Freshly rebuilt local-source 0.9.1 binary passed oversized-reuse 8/8 and body-limit boundary 24/24 HTTP responses. The initially used stale example binary failed those last two cases; its result is excluded from the current-source verdict.
- Isolated PostgreSQL: 20 CRUD operations (100 expected HTTP responses), database startup failure, 2-second connect timeout, query timeout/recovery, and established TCP stall/pool-acquire timeout/recovery all passed with zero unexpected benchmark errors. The HTTP process stayed alive during both runtime database faults and served requests again after recovery.
- `oha -n 10000 -c 64` against Hello World: 10,000/10,000 HTTP 200, 100% success, 31,149 responses/s, p95 5.004 ms and p99 7.893 ms. This is a short local debug-binary/loopback measurement, not a fair Axum-overhead comparison.

## Reproduction and interpretation

Commands used: `cargo audit --db /tmp/mads-full-testing.ORC7FJ/advisory-db`, `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`, `cargo test --workspace --all-features --locked --quiet`, `python3 -m unittest discover -s benchmark -p 'test_*.py'`, and selected `python3 benchmark/run.py --profile smoke --binary-profile debug` cases. The database results were written outside the repository under `/tmp/mads-full-testing.ORC7FJ/`. A first unprivileged workspace test attempt failed when the sandbox denied a CLI test's loopback socket; it was rerun with loopback permission. Likewise, initial benchmark harness socket errors were sandbox-only and disappeared on rerun.

The audit issue is a confirmed vulnerable lockfile dependency, but exploitability through MADS endpoints remains unproven. Other uncovered checklist rows are explicitly untested or application-specific, not passes. No framework implementation was changed during this test run.
